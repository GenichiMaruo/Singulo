# 0.13.0 自動化の追加パフォーマンス改善

基準: `d3c4355c`。作業要求の8tick分散は導入済みで、今回残りの4案を比較検査した。
以下の時刻・時間はベンチマーク全体の計測値で、サーバーのTPSや対応可能台数の保証ではない。

## 採用した変更

| 案 | 実装・採用条件 | 比較結果 |
| --- | --- | --- |
| 作業要求の分散（既存） | 個体ごとに8tickの位相を分ける。生存・キャンセル確認は毎tick維持 | 同時刻の要求集中を軽減。厳密な処理時間上限を設ける方式ではない |
| 経路探索の再試行削減 | 同じ対象への再探索は停止時10tick・移動中20tickを目安に制限。対象変更や新規作業では直ちに再探索できる | 到達不能な同一対象の600tick分の問い合わせが600回→60回 |
| 実行可能工程の待ち行列 | 32工程以上かつ依存数が工程数の4倍以上の場合だけ採用。各判断で完了状態を確認し、変化時に候補を更新 | 512工程・100回の比較で約89.5ms→約2.71ms |
| 画面の共通情報共有と更新抑制 | 在庫・レシピ・注文等を指令台の定期更新ごとに1回集計。個体候補は閲覧者ごとに作る。変化のない定期送信を省く | 20人分の在庫集計20回→1回。変化のない100回の定期更新は送信100回→1回 |
| ストレージ接続情報のキャッシュ | NeoForge標準BlockCapabilityCacheで各面の接続先を保持。数量は常に実インベントリから読む | 2万回の接続先取得で約4.83ms→約1.07ms |

測定環境はJava 21、ActiveProcessorCount=2。比較は専用検査内の連続実行で、JITやGC等の影響がある。
実行可能工程の待ち行列は、すべての注文へ一律には導入しない。小さな注文・単純な依存関係では従来の直接走査を維持する。
複数工程の一括処理では、予定済み工程の判定も線形検索からBitSetへ変更した。

## 安全性と互換性

- 経路そのものはキャッシュせず、探索の試行時刻だけを保持する。開いた通路にも再試行できる。
- 工程の残回数、作業者の能力、作業場所の占有は割当時に確認する。待ち行列が古い数量や貸出状態を固定しない。
- 前提工程が同tickに完了した場合や、必要回数の追加で未完了へ戻った場合にも候補を再構築する。
- 画面の共通部分にプレイヤーごとの操作可能個体一覧を含めない。定期更新でも操作権限を確認する。
- ボタン操作や計画要求への明示的な返信は、内容が同じでも毎回送る。省くのは変化のない定期更新だけ。
- メニューを閉じて開き直したときは最初の情報を必ず送る。保持する前回情報はメニュー単位で、静的なプレイヤーマップは設けない。
- 接続キャッシュはブロック撤去・機能無効化・チャンクの読込状態変更にNeoForgeの通知で追従する。所有元の撤去・復帰でも破棄する。
- チェスト内の数量や予約可能数を長期キャッシュしない。二重チェスト・複数の資材口で同じ在庫を二重計上しない。
- 納品箱が空の場合は搬出先の検索を行わない。未ロードの隣接先へ同期ロードする経路も避ける。

保存形式、レシピ、電力、製作速度、収納容量は変更していない。
既存の作業台収納活用と、満杯時に製作物を地面へ落とさない処理を維持する。

## 検証

追加の5検査:

1. 再探索回数の上限、新しい対象への即時探索、新規作業時のリセット。
2. 接続の再利用、在庫数量の即時反映、撤去・置き換え・明示的無効化・所有元の復帰。
3. 密な依存関係の候補一致、同tickの完了状態変更、実際の作業割当と最寄り作業場所の選択。
4. 共通データの集計回数、閲覧者ごとの候補の分離、同じ画面の送信抑制、再オープン。
5. 2つの資材口から接続した二重チェストの数量一致。

実クライアントでも22画面の操作・描画検査と画像検査を通過。
指令台の注文確認、レシピ記録の各モード、工程詳細などを確認した。

最終の `build runGameTestServer -PtestTickRate=200` は **548件すべて成功**。
配布JARのJava 21・版番号・開発用GUIコード混入検査、翻訳検査、リリース検証スクリプトの10件も成功。
