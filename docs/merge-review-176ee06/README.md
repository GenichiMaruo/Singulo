# マージ済み修正のレビュー

評価日：2026-10-11。対象：[main / 176ee06](https://github.com/GenichiMaruo/Singulo/commit/176ee06e5250e5a28e2669dfe733b227bf40d217)（PR #6、修正本体 `c595f86`）。比較元：`b45f478`。Minecraft 1.21.1 / NeoForge 21.1.256。希望する難易度は「探索と工場づくりを両立する中程度」。

**既定設定の主要な修正は機能しており、Javaのコンパイルと既存GameTest 186件が成功した。一方、追加の再現テストで実装上の問題5件を確認した。正式版にする前に、特にexpertの殻レシピと短寿命設定での進行不能を修正したい。** 計算資料にも、触媒を分数で扱ったことによる過小評価と、現行mainで再計算できない問題が残る。

全指摘・改善案・完了条件は [issue.md](issue.md) に集約した。新規番号はSNG-021以降とし、前回のSNG-001〜020との対応も記録した。

## 確認できた不具合

| ID | 優先度 | 発生条件と影響 | 証拠 |
|---|---|---|---|
| SNG-021 | P1 | `preset=expert`で通常の縮退物質殻に窒素9,000 mBが必要。タンク容量8,000 mBを超えるため加工できない | 実際のRecipeTweaks出力で再現 |
| SNG-022 | P1 | 寿命20分など、許容される設定値で新品の時間結晶からもモジュールを作れない。炉心制御装置などの設備に進めない | 新品24,000 tickに対して必要36,000 tick、レシピ照合失敗 |
| SNG-023 | P2 | 空にして再生期限を過ぎた保管庫で覚醒戦をすると、勝利直後に保管庫を開こうとして再封鎖される | 実際のコンソール・保管庫・ボスで再現 |
| SNG-024 | P2 | 稼働済みアンカーの上限を3→1に下げても3台のまま。保存済みの稼働状態にも上限の再判定がない | 上限変更後の稼働3台を実機テストで確認。保存復帰の経路はソース確認 |
| SNG-025 | P2 | ストレンジ物質版の殻に`shellCoolantMb`と難易度の冷却材倍率が適用されない | `shellCoolantMb=0`でも窒素3,000 mBが残る |

P1は進行・主要機能の阻害、P2は条件付きの機能不整合や重要な評価の誤り、P3は資料・改善項目。expertにはストレンジ物質版の殻という別経路があるので、SNG-021を「すべての入手経路が絶対に停止する」とは判定していない。しかし、通常の圧縮ルートを使えず、危険物の入手に依存するのは難易度倍率の意図から外れる。

## バランス改善の評価

新しいワールド・新しい既定設定では、量子熱機関の下位触媒運転が50 kFE/t、同ティアが200 kFE/tになり、触媒更新の効果が4倍になった。縮退熱炉もBEで1.25 MFE/t、時間結晶で5 MFE/tとなる。下位触媒で次の生産設備を用意し、同ティア触媒へ移行する動機が明確になった。この方向は中程度の難易度に合う。

炉殻の出力24枚・金属の核1個への変更は、点火前の設備バスケットで殻13→7個、岩石63,180→34,020質量、金属6,318→1,701インゴット相当に減る。圧縮の工場を作る必要は残しながら、同じ素材を集め続ける負荷を減らせる。これらの値は通常ルートの静的な資材計算であり、採集・探索・稼働補充を含む所要時間ではない。

発電機の待機制御とPリアクターの回収運転も、初見で資源を失いやすかった部分への有効な変更だった。既存テストで待機・再開、質量上限、過成長した炉心の放出を確認できた。ただし、実際の工場を接続した長期運転や、H凝縮体6個までの一連のプレイは今回の検証に含まない。

覚醒ウォーデンは点火後の任意の目標として自然で、通常戦を強くしない点も適切。ただし、報酬の純増（H凝縮体+1、エキゾチック物質+4、チップ+2／勝利）が工場生産をどの程度置き換えるかは、戦闘時間・死亡率・装備別の実測が必要。通常戦の難易度評価は、再戦の追加だけでは完了しない。

### 育成負荷「136→112分」はそのまま採用できない

既定寿命は54,000 tick、モジュール1個には36,000 tickが必要。切り出した残り18,000 tickを別の触媒の残りと合算する機能はないため、**新品1個から作れるモジュールは1個**になる。

点火前の設備はモジュール6個（炉心制御装置4個＋特異点封入台2個）を要求する。寿命を合算したモデルでは `6 × 2/3 = 4個相当` だが、実際には残量30分以上の触媒を6個用意する必要がある。前回作成したモデルも使用回数を分数の在庫で扱っており、今回の大きな寿命切り出しにはそのまま適用できなかった。この点はモデル側の修正も必要になる。

| 同じ設備バスケットの計上方法 | 新品触媒 | 育成＋種の復元負荷 |
|---|---:|---:|
| 現在の分数モデル | 9個 | 112分・台 |
| モジュール用6個＋別枠の運転用4個を確保し、残寿命をエキゾチック物質4バッチに再利用する例 | 10個 | 124分・台 |
| モジュールを新品1個として計上し、残寿命を加工へ再利用しないモデル | 11個 | 136分・台 |

124分は、元のバスケットが要求する運転用4個を別枠で確保し、モジュールの残寿命から小口加工の触媒消費を賄う条件での加工負荷。育成は10×12分、種の復元は2×2分。発電機での触媒消耗や探索時間は含まない。運転用の4個も設備に転用するなら、その時点の個々の残量と運転需要を追う必要がある。112分を一般的な実プレイ短縮として公表するのは避け、個体ごとの在庫で再計算したい（SNG-026）。

## 検証結果

| 検証 | 結果 | 範囲 |
|---|---|---|
| `compileJava` | 成功 | 本体・生成Java・同じソースセットにあるGameTestをコンパイル |
| 既存`runGameTestServer` | **186 / 186成功** | 既定設定、マージされたテストを変更せず実行 |
| レビュー専用GameTest | **5 / 5で期待する正常動作に失敗** | 上表5件の再現。依存取得失敗ではなく、各アサーションの失敗 |
| 既存`analyze.py` | `AssertionError` | 現行mainでは「停止レシピが4件以上」の旧前提が成立しない |
| モジュールの整数個数評価 | 4個相当と実物6個の差を確認 | 既定寿命・モジュールの実レシピ・同じ設備バスケット |

Java 21のJDKをワークスペースへ取得し、環境のプロキシを明示して実行した。最初の環境にはJREのみでコンパイルできなかったが、JDKの準備後は成功した。通常のゲーム起動・JEIの画面表示・通しプレイ・本番セーブデータの移行は実行していない。

証拠：[既存テストのログ](evidence/gametest-default.log)、[追加ケースのログ](evidence/gametest-review-cases.log)、[個数計算](evidence/module-accounting.json)。レビュー専用コードは [repro](repro/java/io/github/genichimaruo/singulo/test/MergedFixReviewGameTests.java) に隔離して保存した。本体の修正は行っていない。

このドキュメント一式を対象リポジトリの同じ位置に置けば、追加ケースは次で再実行できる。修正前の対象コミットでは5件失敗する想定。

```bash
./gradlew -Dorg.gradle.java.home="$JAVA_HOME" \
  -I docs/merge-review-176ee06/repro/review.init.gradle \
  -PtestNamespace=singulo_review runGameTestServer
```

通常のビルドはこのinit scriptを読まないため、レビュー専用Javaは本体のソースセットに入らない。追加ケースは専用GameTestワールドで一時的に設定値とゲーム時刻を変更し、ケース終了時に戻す。

## 正式版に向けた順序

1. SNG-021〜025を修正し、追加5ケースを成功させる。既存186件も再確認する。
2. SNG-026・030の計算モデルを修正し、コミットと設定を明記した最新の付表を作る。
3. 0.3.0の既存設定を残す更新と、新規ワールドの両方を確認する。旧TOMLに20 MFE/t・炉殻12枚・金属の核2個が保存されていれば、新しい既定値だけでは置き換わらない。意図的な設定変更を保護した移行案内が必要（SNG-027）。
4. standardでT1から初コアまで通し、各ティアの探索・採集・加工待ち時間と触媒補充を記録する。通常戦と覚醒戦、JEI、保存復帰も確認する（SNG-028、前回SNG-017〜020）。
5. 配布物のバージョンを更新し、実際のJARの表示・ファイル名・変更履歴を合わせる。現在の`mod_version`は0.3.0で、0.3.1の変更履歴はdraft（SNG-031）。

現時点では「既定設定の修正は有望で、次のベータを試せる段階」と評価する。正式版の妥当性を決めるには、上の条件分岐の不具合と移行を解消し、通しプレイで中程度の難易度を確認したい。
