# 0.21.0 大規模施設のサーバー負荷

20 TPSで使える時間は1 tickあたり50 ms。今回大きな差が出たのは、別次元の配送便を各ステーションが見つける処理と、流量を使い切った液体幹線で多数の送り手・受け手を組み合わせる処理だった。通常の機械が直接隣へ送電する場合と、複数の設備が同じ経路や候補一覧を共有する場合では、台数を増やしたときのコストが異なる。

## 次元をまたぐ配送

元のステーションは20 tickごとに、別次元へ出した各機の便を確認する。従来は1機調べるたびに、訪問先の次元の全便を先頭から走査していた。対象が同じ次元の全 N 便なら1回の巡回で N(N+1)/2 件を調べる。4,096便なら約839万件で、その確認が同じtickに集中する。

ステーション座標と枠番号で索引を維持し、同じ枠に該当する便の中で元次元を照合するよう変更した。通常の1枠1便では全機の巡回が O(N) になる。追加、削除、次元間の移管、保存からの復元でも索引を更新する。

| 訪問先の便数 | 修正前の全機確認 | 修正後の全機確認 |
|---:|---:|---:|
| 128 | 0.112 ms | 0.033 ms |
| 512 | 0.297 ms | 0.077 ms |
| 2,048 | 3.514 ms | 0.123 ms |
| 4,096 | 12.938 ms | 0.090 ms |

1サンプルで全機を4回確認し、4サンプルのウォームアップ後、11サンプルの中央値を1巡分に換算した。表の時間にドローンの移動AI、描画、未ロードチャンクの起動は含まれない。修正後の短い区間ではJITコンパイルなどの揺れが目立つ。

宛先が決定済みの次元間配送では、再試行のたびに全ポートの行き先一覧を作る処理も改めた。宛先を直接引き、読み込み済みのワームホールの口から最短のものを選ぶ。同じ次元に対象ポート1,000台、使える入口4基、発送待ち100台なら、一斉再試行で従来行っていた約40万件のポート確認と並べ替えが、宛先検索100回と入口確認400回になる。そのほかに読み込み済みの口があれば、入口の確認数はその分増える。これは反復回数からの見積もり。

## 液体パイプ

一本の銅管幹線に、下半分は液体窒素を送り出す機械、上半分は窒素を受ける機械を1本につき1台接続した。すべての組み合わせが中央の同じ細い経路を通る。各試行の前に送り手と受け手を補給・排液し、実際の転送で毎回合計10,000 mBが届くことを確認した。転送は通常5 tickに1回発生する。

| 給液口＋受液口 | 転送1回の中央値（前 → 後） | 95パーセンタイル（前 → 後） | 保持した経路数（前 → 後） |
|---|---:|---:|---:|
| 8＋8 | 0.239 → 0.119 ms | 0.508 → 0.268 ms | 64 → 8 |
| 16＋16 | 0.371 → 0.116 ms | 0.537 → 0.292 ms | 256 → 16 |
| 32＋32 | 0.766 → 0.402 ms | 2.125 → 0.588 ms | 1,024 → 29 |
| 64＋64 | 4.350 → 0.547 ms | 5.300 → 0.665 ms | 4,096 → 57 |

転送本体を8回ウォームアップした後の21回を計測。経路数は全29回の終了時点。各サーバー起動後、最初に動かした8＋8口の初回は修正前40.1 ms、修正後55.5 msを要した。起動直後の初期化やJITを含み得る単発値で、表は運転を続けた際の値を示す。旧実装では送・受各 N 口で N² 通りの経路を保持し、この配置の平均経路長は N 区間あるため、経路配列の参照数は O(N³) になった。分岐も端点もない直管の中間部分は1区間に圧縮される。

修正後は、経路の残量が初めてゼロになったときに、その転送周期内でまだ互いに流せる区間をまとめる。容量を使い切った接続をまたぐ送り手・受け手の組み合わせは経路を構築する前に除外する。周期内に残量がさらに減った場合も、実際に流す経路の残量を都度確認する。送り手・受け手の候補ペア自体は最大 O(N²) で、独立して流せる経路が多い構成では保持経路も増え得る。

同じ次元では各網の転送周期が揃う。64＋64口の上記配置を独立に10組稼働させる場合、各組が実測中央値と同じコストなら、5 tickごとの該当tickに約5.5 ms（20 TPSの時間予算の約11%）を使う計算になる。これは単一網の測定値を足し合わせた推定で、10網同時の実測は行っていない。

## 送電中の施設と工場モニター

4台ずつのSMESセルを四角につなぎ、全セルが隣のセルへ毎tick送電する施設を設置した。各段階で全セルの送電ランプとモニターの蓄電総量を検査した。サーバーが記録した直近100 tickから中央値と95パーセンタイルを計算した。モニター集計はその後に同じ範囲で別途15回計測した。

| 稼働セル | サーバー1 tickの中央値 | 同95パーセンタイル | モニター1回の集計中央値 |
|---:|---:|---:|---:|
| 0 | 0.170 ms | 0.272 ms | 0.022 ms |
| 128 | 0.484 ms | 0.795 ms | 0.299 ms |
| 512 | 0.633 ms | 0.965 ms | 0.689 ms |
| 1,024 | 0.874 ms | 1.475 ms | 1.215 ms |

モニターは画面を開いているプレイヤーごとに20 tickごとに集計する。1,024台の同じ範囲を10人が同じtickに更新した場合、この測定からはサーバー集計だけで約12 msと推定できる。通信時間や他のプレイヤーの処理は別に加わる。また範囲内のドローン・ステーションが257台以上あると通信データの件数上限を超えていたため、工場全体の合計値を送り、個別の明細は近い256台までにした。

## 大規模施設で残る負荷

| 処理と条件 | 増え方と予測 |
|---|---|
| 多数の給電元を一つのケーブル網につなぐ | 1回の給電要求で端点一覧を走査する。給電元 P、端点 E なら、全受け手が満杯でも同tickに最大 P×E 件規模の確認が重なる。給電元100台・受け手100台で各1端点なら約2万件、各400台なら約32万件。受け入れ可能な端点ではさらに供給候補や経路を調べる。 |
| 同じ所有者のドローン発着ポートが多数、空き機体を待つ | 同じ20 tick周期に、待ちポート P 台がそれぞれ読み込み済みの所属ステーション S 台と帰還候補を見る。P=S=1,000、全ステーションが範囲外なら、再試行時に距離判定が約100万回発生し得る。 |
| 迎撃待機中の護衛を同じ狭い場所に集める | 各個体が毎tick、基地の周囲16・32ブロックの個体を探す。100体すべてが互いの探索範囲に入ると、基地の使用者・待機位置の判断だけで約2万～4万件の候補検査になり得る。200体で約8万～16万件。密度を保って基地同士を離す場合は各探索に入る数が抑えられる。 |
| ワームホール・ポートを同じ番号に集中させる | 両端に128台ずつあり、全台が同tickに経路を初めて照会すると、片方向に16,384組の照合が発生し得る。以前は各候補の順位もリストの先頭から調べ、片方向約106万回の追加比較が発生した。今回、口ごとに順位を一度索引化したため、以降は各候補の順位を直接引ける。同番号のポート同士の照合は残る。 |

この表はソースから算出した候補数で、CPU時間への換算には各装置や連携先の処理時間が要る。実測環境は Windows 11、Core i7-12700K、Java 21、Minecraft 1.21.1 / NeoForge 21.1.256 のGameTestサーバー。既定の高速テスト設定（目標200 tick/秒）で動かし、tickの処理時間を記録した。修正前の基準は `9df59bb2`。プレイヤーの移動によるチャンク生成、他modを含む混成工場、長時間運転でのGCは計測範囲外。
