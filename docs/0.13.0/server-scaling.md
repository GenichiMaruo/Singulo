# 0.13.0 サーバー負荷・自動化レビュー

> 作業時点の記録。現在の変更と検証は[最新の調整報告](balance-adjustment.md)と[テスト手順](../development/testing.md)を参照。

対象: `feature/0.13.0`、調査開始時 `8e1c893d`。Minecraft 1.21.1 / NeoForge / Java 21。

## 修正した不具合

- **P1 注文の材料数の桁あふれ**: 深い加工連鎖で乗算が0や負数へ回り込み、在庫なしでも注文可能になる。4096個・64倍の連鎖で修正前に再現。計算可能な数量に余裕を持った上限を設け、超過時は専用の理由を5言語で表示する。
- **P1 大量製作の納品待ちによる停止**: 全工程が終わるまで完成品を納品せず、4096個を全部中間倉庫に置こうとして満杯になる。未完了の工程で使わない完成品はバッチごとに納品可能にした。実AIによる4096枚の製作・納品で検証。
- **P2 将来の余剰品の誤予約**: 計画中に作る余りを、現時点で倉庫にある素材と混ぜて予約・表示する。実在庫と計画上の余剰を分け、余剰は後続工程で利用できるが、既存在庫としては予約しない。
- **P2 範囲カード消失**: スタックから1枚分けてから範囲上限を検査するため、2点目が遠すぎると1枚失われる。検査を先に行う。
- **P2 カタログ参照によるチャンク生成・ロード**: 手順カードの遠方の作業位置、未ロードのリンクの表示や解除で同期ロードする経路を遮断した。

## スケーリングの改善

| 処理 | 以前 | 修正後 |
| --- | --- | --- |
| 注文の再帰計画 | 各依存で全レシピを検索。深さ制限だけでは分岐数が膨張する | 完成品とコンポーネントで索引化。最大8192訪問・1024工程で中断し、不完全な計画は実行しない |
| レシピ棚 | 表示・注文・稼働中の顔表示のたびにカードNBTを再解析 | 棚の各スロットで解析結果を保持。交換、取り外し、保存データ再読込、カードへの直接編集を反映 |
| 在庫維持16件 | 条件確認と計画のたびに同じ倉庫を数える | 確認1回につき実在庫の集計を共有。注文ごとの予約は毎回差し引く |
| 作業場所の競合 | 工程候補ごとに全注文と貸出中の全作業を走査 | 作業割当1回につき占有位置を集計して照合。次の個体の割当では再集計し、古い結果を使わない |
| 時間加速・時間膨張 | 各機械から全ワールドの全時間場を走査 | チャンク別索引で近隣の場だけを照合。同じ場の毎tickの再登録では索引を再構築しない |
| 農作業・伐採・採掘の対象探索 | 最大128³ブロックを一度に走査 | 個体ごとの探索を複数tickに分割。上段から採掘、下段から伐採の優先順位を維持 |
| 指令台の定期処理 | 全台が同じtickに在庫等を確認 | 座標に応じて20tick周期の処理タイミングを分散 |
| 材料の代替候補キャッシュ | 静的マップが無制限に増える | 最大1024件。タグ更新・サーバー終了で破棄 |

持ち物容量の見積もりと工程間依存の構築でも、同じ材料リストの再計算をループ外へ移した。
時間場の値はワールドへの参照を持たず、既存のワールド終了処理でも索引を破棄する。
持ち物に収まる製作回数の探索では、完成品のスタック上限から先に上限を絞り、収まらない大量バッチの繰り返し試算も削減した。範囲探索の座標は再利用し、候補として保持する時だけコピーする。
通常加工機械のレシピ索引、ケーブルの区間圧縮、パネルの受電器単位の処理は既存実装を維持した。

## 検証

修正前の新規回帰テストで、将来の余剰の誤予約・乗算の桁あふれ・再帰計画の走査過多の3件が失敗することを確認。

追加した検証:

- 600レシピから4096個を計画し、2工程への集約、素材512個の予約、保存・再読込後の依存関係を確認。
- 実際に300台の機械と50棚・600レシピを設置し、4096個の計画を50回反復。カード解析結果を再利用し、数量が変化しないことを確認。
- 実AIで4096枚を製作し、納品先から順次取り出す条件で過不足なく納品。素材の残りと落下アイテムも検査。
- 100体の作業者が300件の大量注文から順に割当を要求し、同じ作業場所を二重貸出しないことを検査。この試験は割当処理の検証であり、100体の経路探索の長時間負荷試験ではない。
- 512地点の時間場、30720回の照合、10240回の同一状態更新。球の境界、自身の除外、中心の移動、撤去も確認。既存テストで加速と膨張の相殺・ワールド終了時の解放も検証。
- 大きな範囲の探索が1tickの検査予算を超えないこと、同tickの再呼出しで制限を迂回しないこと、上下段の優先順位を検査。
- 遠方の手順カードを読むだけでチャンクがロードされないこと、カードの直接編集と撤去がキャッシュへ反映されることを確認。
- 在庫維持16件の倉庫走査が1回になること、拒否された範囲指定でカードが減らないことを確認。

既存のドローン高度検査は、他の検査との干渉を避ける専用バッチへ分離し、テスト時計ではなく実際の個体の更新120tickを待ってから同じ高度条件を検査するよう調整した。

最終の `build runGameTestServer -PtestTickRate=200` は **539件すべて成功**。
翻訳、説明文、モデル、実績、支援者データ、リリース検証スクリプトの10件のテストも成功し、Java 21配布JARの検査を通過。

最終実行の参考値（ActiveProcessorCount=2、単発、ウォームアップ条件非固定）:

| 検査全体 | 所要時間 |
| --- | ---: |
| 300台・600レシピで50回の一覧取得と大量注文計画 | 約273 ms（50回の合計） |
| 100体・300件の注文からの割当と競合検査 | 約54 ms（100体分の合計） |
| 512地点の時間場・30720照合と10240更新 | 約42 ms（全操作の合計） |

100体の割当検査の合計は50 msを超えるため、100体が同じtickに要求した際の20 TPS維持を保証する値ではない。

## 性能の解釈と適用範囲

テスト環境の実測時間は単発の参考値で、全サーバーでのTPS保証や上限台数ではない。
100体の自律移動・戦闘、他modの巨大ストレージ、未ロード区間の多い工場などは別の負荷要因になる。
多数の機械・個体のtick処理自体は台数に応じて増える。今回の修正は繰り返しの全件走査、同tickへの処理集中、無制限の計画展開を抑えるもの。
大きな範囲の対象が見つかるまでの時間は延びる場合がある。1tickに集中させず、通常のサーバー処理と共存させるための変更。

今回の変更でレシピ、素材コスト、電力単価、注文上限4096個は変更していない。既存の保存形式を維持する。
