# 0.13.0 アンドロイド作業台の収納活用

> 作業時点の記録。現在の変更と検証は[最新の調整報告](balance-adjustment.md)と[テスト手順](../development/testing.md)を参照。

## 変更

作業台の収納を、製作後の予備の置き場に加え、製作バッチの容量計算にも利用する。
一度に持っていく素材はアンドロイドの持ち物に収まる量までとし、完成品は持ち物と作業台へ分けて保持する。
通常・改良型・量子作業台の既存の27・54・81枠を利用し、収納自体の容量や製作時間・充電消費は変えない。

例: 持ち物が5枠の個体でも、原木320個（5スタック）を一度に持っていき、板材1280枚を作るバッチを計画できる。
台へ置いた完成品はその注文だけの予約として記録し、後続の製作や納品で回収する。
材料の候補を許可したカードや複数工程の一括作業は、引き続き持ち物を基準とした保守的な計画とする。

## 製作物を落とさないための処理

- 実際のレシピから完成品と返却品（空き瓶・バケツなど）を取得し、材料を消費した後の持ち物と作業台へまとめて仮配置する。
- 全品が収まる場合だけ実際の持ち物・収納と注文の予約を更新する。
- 両方が満杯の場合は、その1回分の素材を消費しない。地面へ落とす処理は行わない。
- 製作途中で空きがなくなった場合は、完了した回数を確定し、未製作分を解放する。納品・片付けを経て残りを再開する。
- 他の注文が先に入れた品物は消費せず、新しく収納した個数だけを自分の注文の予約へ加える。
- 持ち物だけで収まる製作では、作業台全スロットのコピーを作らない。収納の仮配置は必要なときにだけ行う。

既存の保存形式と注文の予約を利用する。既存ワールドへの移行処理は不要。

## 検証

追加・強化したGameTest:

1. 5枠の個体が原木320個を持つバッチを受け取り、持ち物容量を超えずに製作規模が拡大する。
2. バックパックのない実AIが板材4096枚を製作・納品する。途中で作業台の収納を使い、最後に収納が空になり、落下アイテムがない。
3. 持ち物と作業台が満杯なら素材と収納を変更しない。既存スタックに空きを作ると再開し、新しく作った4枚だけを予約する。
4. ハチミツブロックと返却瓶4本が同時に収まらない場合は消費しない。両方の空きを作ると全品が残る。通常カードと代替材料カードの両方で検査する。
5. 途中まで完了した作業を解放しても、同じ貸出の完了回数を二重計上しない。

既存の大量注文・多数の登録機械・割当競合・保存・流体搬送なども含めて全体を再検証する。

既存のドローン高度検査は、個体が飛び出した先のチャンクが更新されず時間切れになるケースがあったため、
周囲から離れた平らな床を用意して飛行範囲のチャンクを明示的に読み込み、実際の個体更新を待つようテスト環境を整えた。
この調整は検証環境だけで、ゲーム本体のドローンの挙動は変更していない。

最終結果: `build runGameTestServer -PtestTickRate=200` の **543件すべて成功**。
Java 21配布JAR検査とリリース検証スクリプトの10件のテストも成功。
